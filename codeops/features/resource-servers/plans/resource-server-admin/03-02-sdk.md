# SDK: Resource-Server Admin Management

> **Document**: 03-02-sdk.md
> **Parent**: [Index](00-index.md)

## Overview

The SDK exposes the Admin API through the existing applications domain. It adds exported types and
five methods, uses the existing transport, and validates every response before returning it. The
behavioral contract is owned by [RD-01](../../requirements/RD-01-resource-server-admin.md); this
document specifies the SDK shape.

## Architecture

### Current Architecture

- `ApplicationsDomain` is defined in `packages/sdk/src/domains/applications.ts`.
- Response validators use `isRecord`, `requireData`, and the domain's own type guards.
- The transport builds paths from the `/applications` base and the client adds `/api/admin`.
- Types are exported through `packages/sdk/src/types/index.ts`.

### Proposed Changes

```text
packages/sdk/src/types/resource-servers.ts   # Entity and input types
packages/sdk/src/types/index.ts              # Barrel export
packages/sdk/src/domains/applications.ts     # Five methods and response guard
packages/sdk/tests/resource-servers.spec.test.ts
packages/sdk/tests/resource-servers.impl.test.ts
```

No new domain object, transport, dependency, or client factory is added.

## Implementation Details

### New Types

```ts
export interface ResourceServer {
  readonly id: string;
  readonly applicationId: string;
  readonly slug: string;
  readonly name: string;
  readonly identifier: string;
  readonly audience: string;
  readonly scopes: readonly string[];
  readonly createdAt: string;
  readonly updatedAt: string;
}

export interface CreateResourceServerInput {
  readonly name: string;
  readonly slug?: string;
  readonly identifier: string;
  readonly audience?: string | null;
  readonly scopes?: readonly string[];
}

export interface UpdateResourceServerInput {
  readonly name: string;
  readonly slug: string;
  readonly identifier: string;
  readonly audience?: string | null;
  readonly scopes?: readonly string[];
}
```

### New Methods

Add to `ApplicationsDomain`:

```ts
listResourceServers(appId: string): Promise<ResourceServer[]>;
getResourceServer(appId: string, resourceServerId: string): Promise<ResourceServer>;
createResourceServer(
  appId: string,
  input: CreateResourceServerInput,
): Promise<ResourceServer>;
updateResourceServer(
  appId: string,
  resourceServerId: string,
  input: UpdateResourceServerInput,
): Promise<ResourceServer>;
deleteResourceServer(appId: string, resourceServerId: string): Promise<void>;
```

### Response Validation

Add `isResourceServer(value: unknown): value is ResourceServer` in the applications domain (or a
small local helper). It checks:

- `id`, `applicationId`, `slug`, `name`, `identifier`, `audience`, `createdAt`, `updatedAt` are
  strings;
- `scopes` is an array of strings.

`listResourceServers` uses `requireData` with an array guard; single-resource methods use
`requireData` with `isResourceServer`. A malformed response throws the SDK's existing
`PortaError`/validation error path; it never returns a partial object.

### Paths

| Method | Transport path |
| --- | --- |
| list | `GET /applications/${appId}/resource-servers` |
| get | `GET /applications/${appId}/resource-servers/${resourceServerId}` |
| create | `POST /applications/${appId}/resource-servers` |
| update | `PUT /applications/${appId}/resource-servers/${resourceServerId}` |
| delete | `DELETE /applications/${appId}/resource-servers/${resourceServerId}` |

`appId` and `resourceServerId` are passed through as path segments; the server owns UUID-or-slug
resolution. The SDK does not add client-side path validation beyond the existing transport.

## Code Examples

```ts
const servers = await client.applications.listResourceServers('acme');
const created = await client.applications.createResourceServer('acme', {
  name: 'Billing API',
  identifier: 'https://billing.example.test',
  scopes: ['billing:read'],
});
const updated = await client.applications.updateResourceServer('acme', created.id, {
  name: created.name,
  slug: created.slug,
  identifier: created.identifier,
  scopes: ['billing:read', 'billing:write'],
});
await client.applications.deleteResourceServer('acme', updated.id);
```

## Error Handling

| Error Case | Handling Strategy | AR Ref |
| --- | --- | --- |
| Non-2xx API response | Existing transport error with status/body | RD-01 |
| Malformed success body | SDK validation error, no partial object | RD-01 |
| Missing resource | Server returns `404`; SDK surfaces it | RD-01 |
| Permission failure | Server returns `403`; SDK surfaces it | RD-01 |
| Delete success | `204` with no body; method resolves `void` | RD-01 |

## Testing Requirements

- Spec tests for each method's path, method, body, and parsed result (ST-13–ST-15).
- Failure tests for malformed success bodies and non-2xx responses.
- Type-contract coverage through the SDK's existing typecheck project.
- No network or database dependency in SDK tests; use the existing transport test double.
