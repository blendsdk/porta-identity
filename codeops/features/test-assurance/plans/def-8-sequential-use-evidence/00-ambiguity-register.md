### Resolution Notes

**AR-1:** DEF-8 is a test-assurance defect, not a new RD. The plan declares `Implements: test-assurance/RD-05` to match the DEF-21 plan and keep roadmap/selector matching deterministic.
**AR-2:** The generic seam `createHumanAuthCasesContract()` currently throws `HUMAN_AUTH_LIVE_ADAPTER_UNAVAILABLE` in live mode (`human-auth-cases-adapter.ts:8`). The immutable boundary spec runs all sentinels through that seam, so live mode must remain scoped and fail closed for anything it cannot observe for real.
**AR-3:** The requirement catalog is immutable; a partial observation cannot satisfy `observeCase` without fabricating facts, so all 21 steps are implemented.
**AR-6:** Magic-link and password-reset already emit rejection audit events (`user.magic_link.failed`, `user.password_reset.failed`); invitation does not. The fix adds the missing event on the invalid/used/expired path only.
**AR-7:** Defaults (900s / 3600s / 604800s) are infeasible to wait for; the catalog minimums (60s / 300s / 300s) are the only non-DB route. The three expiry artifacts are issued together and awaited once (~300s), then consumed.
**AR-22:** `human-auth-live` is intentionally service-free today; adding a service-requiring spec would break `assurance:test --select human-auth-live`. The live spec therefore lives in the harness block and its own selector; only the adapter's pure helpers (if any) may join `human-auth-live`.
**AR-26:** Checked against `_shared/zero-ambiguity-gate.md` §Complexity Escalation Gate: explicit exemption for “tests that directly prove accepted behavior using existing project patterns”. The invitation audit is ordinary feature code. No larger machinery is proposed, so the gate does not fire.
**AR-29 (runtime):** Discovered while implementing the live ST-46 adapter. Magic-link binds an artifact to a presented interaction authority (`magic-link.ts:190-213`), so `wrong-recipient` rejection is reachable by presenting a mismatched `?interaction`. Password-reset and invitation have no such input: the reset and accept-invite handlers resolve the user solely from the token, and invitation token lookup is not scoped by organization. The abstract AR-17/AR-16 resolutions therefore do not map to those flows.
**AR-29 resolution:** The user chose to fix the real bug and report the rest truthfully. An organization-scoped invitation-token lookup is added so an alpha invitation presented under the bravo slug is rejected with `invalid-artifact` (Phase 2, Step 2.4). The remaining reset/invite `wrong-recipient` behavior is implemented exactly as the adapter observes it and, if it accepts, is recorded as a requirements-level finding against ST-46 rather than hidden or weakened. No immutable requirement catalog is edited within DEF-8.
**AR-30 resolution:** The user chose the truthful ST-46 gap. The adapter never exhausts the shared global admin limiter. For `invitation-throttled-request` it makes a bounded set of equivalent-input issuance attempts (well below the global admin budget of 60 writes/60 s), observes that invitation issuance is not throttled per equivalent public input, and returns those observed facts with a `securityLog` that does not match the required normalized class. ST-10/ST-11 therefore fail for that probe and are recorded, with AR-29's reset/invite `wrong-recipient` acceptance, as ST-46 requirements-level findings. The shared admin limiter is preserved for the rest of the block, including the TTL restore.
**AR-31 resolution:** The user chose the admin user projection as the durable-effect basis. Each accepted consumption fingerprints `GET /api/admin/organizations/:orgId/users/:userId` before and after and requires exactly one changed resource key, so `durableEffectCount` is `1` for magic-link (login/verification fields), password-reset (`passwordChangedAt`), and invitation (`emailVerified`). No session follow-through and no membership expectation are used; AR-12's "membership for invitation" assumption is superseded.
**Consequence:** Because AR-29 and AR-30 accept truthful ST-46 failures, the harness run may report ST-46 as failed for the `password-reset-wrong-recipient`, `invitation-wrong-recipient`, and `invitation-throttled-request` probes. Success criterion 3 in `99-execution-plan.md` is updated from "passes ST-46" to "records the truthful ST-46 outcome and its findings".
