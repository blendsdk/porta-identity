## Resolution Notes

**AR-1:** `packages/server/src/users/gdpr.ts:116-120` selects from `user_claim_values` joined to `claim_definitions` on `definition_id`. Migration 007 defines `custom_claim_values` with a `claim_id` foreign key to `custom_claim_definitions`. The confirmed fix is the corrected SQL; no compatibility view is introduced because the unit test mock hid the defect and no other source query uses the wrong names.

**AR-2:** The server validates the slug through Zod at `packages/server/src/routes/organizations.ts:98-100` — a malformed or reserved slug is a `400` response, while a well-formed but taken slug answers `200 { isValid: false, error: 'Slug already in use' }` (`packages/server/src/organizations/service.ts:475-492`). The SDK type and its documentation must state both paths.

**AR-3:** `ListParams` (`packages/sdk/src/types/common.ts:23-26`) forwarded `sort`/`order` verbatim; the server only reads `sortBy`/`sortOrder` (`packages/server/src/routes/organizations.ts:84-95`), so a caller's `sort` was silently dropped and results fell back to `created_at`. The index signature on `ListParams` had hidden this from the compiler.

**AR-4:** The organization and user history routes pass `getEntityHistory`'s `{ data, hasMore, nextCursor }` envelope through (`packages/server/src/lib/entity-history.ts:42-46`; `organizations.ts:291-299`, `users.ts:435-447`). `getEntityHistory` supports only `organization` and `user` (`entity-history.ts:57-60`); the application and client routes call it with unsupported entity types and answer `500` (`entity-history.ts:132-135`; `applications.ts:315-325`, `clients.ts:434-441`). The SDK's `requireData(..., Array.isArray)` guards in those two domains return the bare array and drop `hasMore`/`nextCursor`; both the server defect and the guard behavior are recorded in the separate follow-up issue. The SDK fixes cover organizations, users, and standalone users.

**AR-5:** ETag emission sites verified at `packages/server/src/routes/users.ts:301` (org-scoped update), `:805` (standalone update), `packages/server/src/routes/organizations.ts:239` (update), and `packages/server/src/routes/two-factor-admin.ts:360` (policy update). The user-create route sets none; AR-17 adds the emission. `POST /organizations` and the claim writes set no ETag, so they are excluded.

**AR-6:** There is no `/organizations/:orgId/users/:userId/claims` prefix in the server router. The application-prefixed routes live at `packages/server/src/routes/custom-claims.ts:109-247` under `admin:claim:read`/`admin:claim:update`. The list endpoint answers `{ data: [{ definition, value }] }`, and the single-value endpoints answer `{ data: { id, userId, claimId, value, createdAt, updatedAt } }`. The `:appId` path segment is not a value filter: the list route passes only `userId` to `getValuesForUser`, which returns values across all applications (`packages/server/src/custom-claims/repository.ts:492-501`), and the single-value routes resolve by `userId` and `claimId` only. The SDK documents this behavior instead of implying application scoping.

**AR-7:** The server's `CustomClaimDefinition` (`packages/server/src/custom-claims/types.ts:36-47`) uses `claimName`/`claimType`/`includeInIdToken`/`includeInAccessToken`/`includeInUserinfo`. The old SDK type described a different, nonexistent resource, and the existing `claims` CLI command printed a `claimSlug` field that the server never sends.

**AR-8:** The permissions route requires `admin:role:read` (`packages/server/src/routes/user-roles.ts:204-222`) and returns a deduplicated `Permission[]` via `getUserPermissions` (`packages/server/src/rbac/user-role-service.ts:177-183`).

**AR-9:** `UserDataExport` is defined at `packages/server/src/users/gdpr.ts:21-66` and returned verbatim by the export route. The SDK mirror is a type-only export; no runtime validation is added.

**AR-10:** The SDK is published at `1.11.0`; its changelog already documents a breaking `InviteUserResult` change in a minor release. This plan records the migration in `packages/sdk/CHANGELOG.md` under `Unreleased` and leaves version constants to `scripts/sync-versions.js` and the release workflow. `AGENTS.md` explicitly forbids hand-editing version-derived constants.

**AR-11:** `RESERVED_SLUGS` (`packages/server/src/organizations/slugs.ts:24-54`) has no `new` entry. Adding it changes validation only; existing rows are untouched. An organization already created with the slug `new` keeps its data and is always reachable by UUID. No API rename exists — the update schema and repository field map do not accept `slug` (`packages/server/src/routes/organizations.ts:70-75`, `packages/server/src/organizations/repository.ts:185-196`) — so the operator note documents UUID access and a direct database slug change. Portability manifests containing slug `new` no longer pass the shared slug validator on import (`packages/server/src/portability/schema.ts:105`); the note documents the manifest workaround.

**AR-12:** `packages/cli/src/commands/user-claim.ts:69,120,152` calls `sdkClient.userClaims`, whose routes return `404` today, so the CLI subcommands are already non-functional. The fix keeps the command names and adds the missing `--app` scope explicitly.

**AR-13:** The plan set is `codeops/features/sdk-server-contract-drift/plans/sdk-contract-truth/`, with the feature's own `requirements/` directory as the source of RD-01 and RD-02.

**AR-14:** Application and client history methods are deferred to a separate server defect: their routes fail with `Unsupported entity type for history` and cannot be fixed SDK-side (AR-4). The remaining related defects — claim-definition types and the claim-definition CLI surface — are closed here. The `usersById.getHistory` unwrap shape is pinned by a test rather than reworked, because `unwrapData` already returns the inner envelope correctly.

**AR-15:** The server joins claim values with their definitions for list responses (`packages/server/src/custom-claims/repository.ts:443-466`), so list items carry `{ definition, value }`. The single-value endpoints return only the stored value row. The SDK mirrors both shapes instead of the previous flat, nonexistent `UserClaimEntry`.

**AR-16:** Detected commands: `yarn verify` (root; structure tests plus Turbo verify for server, SDK, and CLI) and `yarn test:integration` (needs PostgreSQL, Redis, MailHog via `yarn docker:up`). `yarn test:structure` runs standalone. No new harness profile is added; the retained tenant-admin compatibility probe is updated with the SDK contract and the registered `yarn assurance:compat` tenant-admin selector runs in Phase 4 from a clean committed revision.

**AR-17:** Verification showed the create handler assigns `ctx.body` without calling `setETagHeader`; the issue's cited line 279 belongs to the `GET /:userId` handler. Adding the emission line is a one-line change that reuses the existing helper and matches the adjacent `PUT` handler (`packages/server/src/routes/users.ts:301`). It introduces no new machinery and no data change.

**AR-18 (runtime):** The revived type-compatibility oracle was dead before this plan (excluded from every typecheck program), so the Client mismatch went unnoticed. The SDK's narrower unions are deliberate consumer ergonomics, and the server route decorates client responses with `effectiveLoginMethods` (`packages/server/src/routes/clients.ts:189-213`), which the server domain `Client` type does not model. The oracle compares `Client` in the SDK→decorated-response direction only; the reverse cannot hold while the server keeps unconstrained strings, and changing either product type is out of this plan's scope. All other entity comparisons keep both directions.
