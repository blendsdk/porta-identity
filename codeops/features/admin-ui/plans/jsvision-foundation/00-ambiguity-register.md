### Resolution Notes

**AR-1:** The feature and plan names were confirmed after repository layout detection identified the nested CodeOps layout.

**AR-2:** The milestone stops after an authenticated, testable application skeleton. Organization, user, application, client, key, audit, session, configuration, import, export, and other administration screens require later decisions.

**AR-3:** The existing `porta gui` implementation and registration will be removed as part of the replacement. Backward-compatible aliasing is outside the confirmed scope.

**AR-4:** The CLI owns the TUI implementation and its JSVision dependencies; it will not dynamically discover a separate Porta admin package.

**AR-5:** The new environment is part of the feature modification set. Its hostname must resolve through public DNS to IPv4 loopback, run a resolver preflight before container startup, bind published ports to `127.0.0.1`, use host-only cookies, and remain explicitly non-production. AR-9 through AR-15 and AR-23 own the resolved lifecycle, hostname, ports, TLS, and bootstrap details.

**AR-6:** Integrated authentication reuses one UI-neutral login coordinator from both `porta login` and `porta admin`; it does not spawn another CLI process. Browser-open failure presents the authorization URL and manual completion inside TUI-owned input so readline never competes with JSVision for the terminal.

**AR-7:** The selected-server guard is required because global options can override the credential file's server while the refresh grant deliberately targets the server recorded in that file. A 401 or refresh failure returns to unauthenticated state; a 403 from an administrative operation is an authenticated-but-unauthorized result.

**AR-8:** Ordinary shutdown preserves exploratory data. Reset is the deterministic clean-start path and rotates runtime secrets together with the data they protect.

**AR-9:** The recommended hostname currently resolves only to `127.0.0.1` and has no AAAA record. Startup checks both conditions before creating containers.

**AR-10:** Stable configurable ports keep the OIDC issuer and stored credential target predictable. Internal-only data services avoid the existing host Redis collision and minimize exposure.

**AR-11:** A trusted local certificate avoids browser warning interstitials and exercises the intended HTTPS path. Generated certificates and keys remain ignored and uncommitted.

**AR-12:** Interactive bootstrap uses the existing hidden-input path. Automation, if later required, may use only an owner-readable temporary password file that is deleted before bootstrap; secrets never enter argv or a committed environment file. SMTP is routed to the playground MailHog service from the first milestone so invitations, recovery, OTP, and other future email journeys can be inspected. The bootstrap identity is `admin@playground.porta.test`; `porta init` marks it verified, while later invitation, recovery, OTP, and notification messages remain observable in MailHog.

**AR-13:** Persistent encrypted signing data requires stable encryption keys. Regenerating keys while retaining the database would make protected data unreadable.

**AR-14:** Reset warns that credentials for the playground URL become stale; the integrated authentication flow repairs that state on the next launch without deleting credentials that may belong to another environment.

**AR-15:** One lifecycle entry point owns DNS, port, certificate, secret, Compose, migration, initialization, health, and exact cleanup ordering. The generic developer stack and retained black-box harness remain unchanged.

**AR-16:** The current credential store owns one profile. The foundation milestone prevents silent replacement but does not introduce profile selection, migration, naming, or concurrent credential storage.

**AR-17:** The SDK remains read-only by default. The CLI opts into persistence through callbacks because it owns the credential path and filesystem policy. Persistence failure rejects the refresh with a distinct storage error, retains the validated update only for retrying the same atomic write, and never repeats a grant with a potentially consumed refresh token. Stored and refreshed credential shapes are validated, the optional refresh-token type is aligned between CLI and SDK, and a short lock coordinates concurrent CLI processes.

**AR-18:** Server input accepts an origin only: HTTPS scheme, hostname, optional port, no embedded credentials, path, query, or fragment. Explicit `--insecure` relaxes certificate verification, not the HTTPS requirement.

**AR-19:** JSVision's production host owns raw mode and terminal restoration. Headless tests construct the real application without calling the native host run path.

**AR-20:** The shell proves application construction, menu/command routing, async authentication state, focus, resize, status rendering, and clean quit. It intentionally does not invent organization, application, client, user, key, audit, configuration, session, import, export, or dashboard behavior.

**AR-21:** Standard JSVision controls supply mouse behavior where available, but every required action remains reachable by keyboard and is not communicated by colour alone.

**AR-22:** The UI-neutral session and login services do not import JSVision. Presentation receives injected capabilities and never owns tokens, filesystem writes, or network protocol rules.

**AR-23:** The lifecycle command is idempotent against an initialized persistent database. Bootstrap password entry remains interactive and hidden; automation is not added by this plan.

**AR-24:** Public documentation describes the shipped CLI without the reserved test namespace. Technical documentation records exact playground commands, URLs, reset consequences, MailHog usage, and non-production restrictions.

**AR-25:** Specification tests precede implementation. SDK contract changes additionally require the repository's clean-revision compatibility workflow; authentication changes require relevant protocol/security assurance evidence, and browser-mediated behavior requires UI/harness evidence.

**AR-26:** Diagnostics preserve actionable categories such as unavailable, unauthenticated, unauthorized, invalid configuration, and storage failure without echoing sensitive or attacker-controlled detail.

**AR-27:** The existing login path uses `decodeJwt()` without authenticating the ID token and sends no nonce. The project security invariants prohibit carrying this forward. Refreshed ID tokens are not persisted as replacements unless they pass the same validation; otherwise the last validated identity is retained and live identity comes from the UserInfo verification step.

**AR-47:** The admin UI is part of Porta and follows Porta's current Node 24 LTS development and verification workflow. No separate platform/runtime qualification matrix, probe script, or temporary GitHub Actions workflow is part of this feature.
