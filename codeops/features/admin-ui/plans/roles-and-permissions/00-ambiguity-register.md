## Resolution Notes

**AR-1 through AR-6:** These entries import the user's approved RD-05 decisions and passed preflight
rulings. They are not reopened during planning.

**AR-7:** The existing routes use `204` for void mutations, but that status cannot carry the
server-derived reauthentication result. The proposed JSON result applies to role-slug update,
role/permission deletion, role-permission removal, and user-role removal. Additions retain their
existing result behavior. A no-op removal never reports reauthentication because it changed no
authority.

**AR-8:** `account-finder.ts` already omits application custom claims when client context is absent.
The proposed RBAC behavior follows that least-authority pattern and never falls back to a global
role or permission union. A real database/query error still follows the existing fixed failed-account
path rather than being disguised as an empty authorization result.

**AR-9:** Existing role and permission deletion services duplicate the same database revocation SQL,
and `deletion-cleanup.ts` already owns detached post-commit Redis key deletion and OIDC payload
scanning. The proposed helpers centralize only this directly repeated behavior; they add no service,
worker, queue, or generalized cleanup framework.

**AR-10:** Existing Application workspace/controller files are 476/472 lines and User
workspace/controller files are 589/715 lines. Directly adding both application RBAC and user-role
workflows would exceed the project size guidance. Feature-local modules retain the established
state/service/controller/workspace pattern without introducing a cross-context mega-controller.

**AR-11:** The proposed set is derived from AGENTS.md, workspace manifests, RD-05 verification
requirements, and the registered assurance command grammar. Root `yarn verify` remains prohibited.

**AR-12:** The internal provider metadata key is an implementation bridge, not a public claim.
Only account claim construction consumes it. Specification coverage proves it is absent from ID
tokens, UserInfo, introspection, discovery, rendered login/consent/error content, and logs. Logger
redaction is a backstop rather than permission to log the provider metadata object.

**AR-13–AR-19:** These entries record the user's accepted plan-preflight recommendations. They add
only missing production wiring, precise recovery wording, canonical immutability, maintenance of
known affected tests, existing SDK validation primitives, and extraction of already-present SQL.
They introduce no new infrastructure, migration, worker, policy layer, generalized framework, or
dependency.

**AR-20:** Execution exposed two test-order defects, not product ambiguity. The delegation oracle
now supplies the target role needed to reach each intended authorization branch. ST-9 remains an
immutable Phase 1 specification, but its green gate follows the Phase 2 canonical mutation guards
that implement it. The user approved both corrections without changing expected behavior.

**AR-21:** The Phase 4 spec-author correctly captured the required behaviors but modeled controller
dependencies as raw SDK arrays. The approved terminal adapter returns fixed sanitized results, and
existing Admin controllers read those adapters through a lazy `readOperations` seam. Changing only
the test harness types and mock return envelopes preserves every behavioral assertion while
avoiding a second result contract or normalization shim.

**AR-22:** The Phase 4 red baseline hid harness-only defects behind the expected missing-module
failures. Current JSVision closes modals through `loop.endModal`, exposes keyboard participation as
`focusable`, and nests the action row below a page layout group. The harness now gives both standalone
pages bounded DSL layout instead of adding unbounded page roots directly. The corrected assertions
preserve the intended cancellation, keyboard-reachability, and grid-spacing behaviors without adding
obsolete test compatibility to production code.

**AR-23:** The recorded modification set assumed the existing Application/Client composition could
absorb complete RBAC orchestration. It is already 653 lines, leaving too little room for RBAC state,
controller, dialogs, intent dispatch, cancellation, session ownership, recovery, and disposal. An
independent minimum-sufficient-design review recommends one `application-rbac-features.ts` owner
whose public seam remains specific to Application RBAC. General feature, CRUD, dialog, dependency-
injection, or lifecycle abstractions remain prohibited. The user approved this exact boundary.

**AR-24:** The existing Application workspace specification fixes the complete tab array to Overview
and Modules. The approved RBAC specification fixes the same array to Overview, Modules, Roles, and
Permissions. Production code cannot satisfy both immutable oracles. The required correction changes
only the older exact title array and preserves all of its existing surface, action, and layout checks.
The user approved this correction.

**Gate confirmation:** The user confirmed the complete planning scope and AR-7 through AR-24 after
repeatedly requiring an overengineering check. The accepted baseline adds only direct feature code,
two narrow authority helpers, one extraction of existing survivor SQL, and the focused Application
RBAC coordinator approved in AR-23. No unresolved gate remains.
